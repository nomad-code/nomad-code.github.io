The loop is the forcing function

bunpro replays the clip until you come back and press 2 · chrome MV3, unpacked

First cut of this auto-advanced the queue on the audio's ended event — clever, and the wrong deliverable. The version worth having is dumber and does more work: replay the same line, forever, with a gap, until you move the card. The repetition is what pulls you back to the keyboard. And since it's already counting ended events to know when to replay, it may as well keep the number — how many times did I have to hear this line before it landed? — which is the one thing Bunpro's SRS doesn't record.

01

The loop

playing— ended, count++ → gap→ playing…until new clip→ bank the card, reset to 0

Replay fires on the audio element's real ended event, never a timer, so the gap you set is genuinely a gap and a long sentence never gets clipped. Cards are keyed by clip src rather than element identity — a front-end that reuses one <audio> and swaps its source still reads as a new card. The badge carries both numbers:

Seven replays of this line, one hundred and forty-three this session.

02

Why it needs the page's own JS context

A content script shares the DOM but not the JavaScript world. Fine for an <audio> tag rendered into the page — useless for a clip built with new Audio(...) and played without ever being attached, which is how plenty of SRS front-ends do it. So there are two scripts, and no Bunpro selector in either:

◍

inject.js — MAIN world

Wraps HTMLMediaElement.play and the Audio constructor, plus a MutationObserver for DOM-rendered clips. Every clip gets an id, a src and an ended listener. Reports up as CustomEvents, takes play/stop back down.

⧗

content.js — isolated world

Owns the loop, the counts, the badge, the keys. Never touches media directly — it asks the bridge. That split is why the thing has no idea what Bunpro's DOM looks like.

03

Pressing P is the fallback, not the mechanism

Asking for the P key is asking for "play the clip again" — but the key is the least reliable way to say it. If a clip is reachable the bridge plays it directly: no focus games, no interference with typing, works when the shortcut is disabled inside an input. The synthetic keypress only fires when nothing is reachable at all.

And when it does fire it has to be careful. Dispatched KeyboardEvents are untrusted — they reach a site's handlers but can never type — so a printable key aimed at a focused answer box is simply swallowed by it. The field gets blurred for the dispatch and refocused after, except within 1.5s of a real keystroke, where stepping focus out would eat a character mid-answer.

document.addEventListener('keydown', e =>
  console.log(e.key, '| code:', e.code, '| target:', e.target.tagName), true);

Console that on a review page, press the key you actually use, put what prints in the popup.

04

The count wants to leave

Replay count is a different signal from pass/fail, and it's the one that says this line is not in your ear yet even on cards you're answering correctly. Copy log puts the whole history on the clipboard as CSV — at, loops, clip — one row per card. That's deliberately the cheapest possible export: when the SRS side moves off Bunpro and into the local filesystem, this is already a file, not an API integration to unwind.

05

What's untested

  • No live logged-in review session was driven. The design is selector-free, so the likely first-run failure is the fallback key, not the loop.
  • Bunpro's real shortcut map is unverified — p is an assumption.
  • Whether clips are DOM-rendered or built in memory is unknown; both paths exist, only one gets exercised in practice.
