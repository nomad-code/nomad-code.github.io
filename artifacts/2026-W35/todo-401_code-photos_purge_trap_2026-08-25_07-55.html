the trap

a photo edited on 2026-08-15, render still iCloud-side:
  original → exported to ~/ark ✓  →  uuid lands in export db
  _edited render → missing ✗  →  reported, then discarded

purge asks one question — “is the uuid in the export db?” — gets yes,
and deletes a photo whose edit existed nowhere but iCloud.
fix: common.hold_uuids = hasadjustments and not path_edited, subtracted from the safe set. Computed live, never stored — an asset releases itself the moment its render lands, so a hold can never become permanent. Second bug, same rock: the osxphotos report has no uuid column, but parse_report keyed on one — every row collapsed under "", so known_orphans could never match and missing rows logged as MISSING (not a known orphan): with nothing after the colon. Now keyed on filename. 12 new tests, 130 green.

Two in five assets in the library are screenshots already sitting on the Mac. They round-trip through iCloud to be indexed, then get purged, then come back — a sawtooth paid for in upload bandwidth and COLDLINE storage. photos.db can index them where they already are. That is the recurring-weight fix; the purge is only the symptom.

one roof, already built

The ask — Apple, Pixel, Telegram, Mac, WhatsApp under one cognitive roof — is the schema that already exists: photo = the canonical dedup'd event (captured_at, lat/lon, phash, content_sha256); instance = N provider copies hanging off it (provider, provider_uid, ark_path). Apple and the Google Takeout are already in it. Everything else is an adapter, not a new system.

But the 2TB premise needs correcting: iCloud Photos is all-or-nothing. “Optimize Storage” only chooses which resolutions cache on-device — every asset still counts against quota. A 2TB iPhone cannot be free overflow inside Photos.app. To spend device storage instead of iCloud storage the media must live outside the Photos library — or you keep iCloud lean and stage trips on demand, which is exactly what recall already does.
