The map now remembers.

It loaded every time because two different things forgot their work: the server rebuilt the Nearby page, then the browser rebuilt the Google Map. Both layers now reuse what they already know.

Can it be better or cached?
Yes. Cache the page briefly; reuse the map for the life of the tab.

Five-minute ISR removes repeat database rendering. reuseMaps keeps the same Google Maps instance across Search → Locations navigation, so the warm return no longer shows a blocking map loader.

Root cause

Three waits, stacked

The Google API script itself was already loaded once. The repeated wait came from page rendering, a fresh map constructor, and treating every remount as cold.

Dynamic page

The Nearby routes had no revalidation policy, so every request ran the location queries again and returned private, no-store.

Fresh map instance

Client-side tab navigation unmounted the map. Returning constructed another Google Map instead of reusing the compatible instance.

Blocking tiles gate

Every mount reset isLoading and covered the map until tilesloaded, even when that map type had already rendered in this tab.

Design

Two caches, two lifetimes

Caching is split deliberately. Server data gets a bounded freshness window; the expensive visual object lives only inside the current browser document.

1 Server · 5 minutes

Next.js ISR

Nearby location HTML and server queries are shared, then revalidated after 300 seconds.

2 Browser · current tab

Google Map reuse

Compatible map instances survive component remounts. Ready map types skip the repeat blocking loader.
