portal-v2, the monorepo

The title questions answered: Turborepo yes. pnpm no — it's Bun. And the interesting part is how little Turbo is asked to do. This is the cognitive-debt fill on how the repo actually works, read from upstream main via the nomad-code mirror.

package manager

Bun 1.3.8

Plain npm-style "workspaces": ["apps/*","packages/*","tools/*"] in root package.json, read natively by Bun. bun.lock text lockfile. No pnpm-workspace.yaml anywhere; the only pnpm mentions are vendored docs and scaffold boilerplate.

orchestrator

Turborepo, thin

Task fan-out and caching only. There is no ^build anywhere — zero topological cross-package ordering expressed in turbo.json. Remote cache via TURBO_TOKEN/TURBO_TEAM in CI.

toolchain

mise above it all

Pins node 22, bun 1.3.8, sops, age, plus npm CLIs (sass, rtlcss, clean-css). File-based tasks: db:import, db:anonymize, server:env. Auto-loads app .env into the shell.

the stack, top to bottom

misetoolchain versions + ops tasks (db import/export/anonymize, server env assembly). The entry point: mise run setup → mise install + bun install.
buninstalls, workspaces, test runner (bun test + happy-dom preload), script runner, and patchedDependencies (a newrelic double-instrumentation guard patch).
turbotask graph + cache. bun dev = turbo run dev //#dev:css //#dev:css:trigger — one app dev server plus two root-package watch tasks.
biomelint + format, run directly at root (not through turbo). Scoped to apps/** and packages/** minus design-standards; tools/** is unlinted.

the one workspace edge — wired outside turbo

Exactly one cross-package dependency exists: apps/portal → packages/design-standards (a git subtree of the org-wide Bootstrap theme, also shipped as a RubyGem). Turbo doesn't know about it. It's consumed four ways:

  • Raw source import — portal imports src/javascripts/react-helpers JSX directly; transpilePackages compiles it; types are hand-written in a local .d.ts.
  • SCSS load path — next.config adds the package's node_modules to sassOptions.loadPaths.
  • postinstall asset copy — portal's postinstall builds the package and copies dist/ into public/vds/ (dist is gitignored).
  • CDN fallback — NEXT_PUBLIC_VDS_BASE_URL flips between the local copy and jsdelivr.

The lesson: a monorepo doesn't oblige you to route every edge through the build tool. This edge is odd (subtree + gem + asset pipeline), so it gets bespoke wiring, and turbo stays honest about what it manages.

ship path

  • PR → one CI job: bun install --frozen-lockfile → bun run ci:run (lint+build+test, turbo remote cache).
  • Push to main → self-hosted runner runs scripts/deploy.sh: Capistrano-style timestamped releases (keep 5), output: standalone with outputFileTracingRoot at repo root, rsync + symlinked shared .env, systemd restart. No containers in prod; docker is dev-only (Postgres + pgadmin + devcontainer).
  • Rollback → dispatch workflow, rollback.sh <release-timestamp>.
  • Two deploy warts worth remembering: Bun's hoisting needs manual symlinks so NODE_OPTIONS="-r newrelic" resolves, and the OTel bridge needs its deps linked beside the agent.
