4. Plan exchange protocol

Continue the plan passing Brendan has begun. Do not create a second competing implementation plan in BPO-LINK.
1. Fable audits or revises its lane's plan and returns a named revision, concrete changes, unresolved choices, and evidence paths.
2. Paired Astra reads that exact revision. Findings identify severity, affected requirement, proposed correction, and acceptance evidence. Disagreement is resolved against the user's intent and source facts, not by treating the other model as authority.
3. Fable incorporates or explains each finding. Astra checks the resulting revision and records accepted, rejected-with-reason, or still-open dispositions.
4. BPO-LINK relays only cross-lane dependencies and shared-shell findings, with source lane and revision. Lane-specific business requirements remain in their lane plan.
5. Freeze an accepted execution baseline after blocking findings are resolved. Later changes carry a short delta and impact assessment. Do not restart the whole plan audit for every cosmetic change.
Plan review and implementation have separate states. An accepted plan is not a started worker. A start command must name the accepted revision and deadline, and the worker must acknowledge both.
For review convergence, aim for two focused exchanges, then classify remaining items as blockers or deferred improvements. This is a proposed timebox, not an instruction to override Brendan's ongoing review.

6A. The universal product loop: source → canvas → chat → agent

DSP is continuing product work across Brendan's contexts, not merely a stylesheet extraction or a one-off FIT demo. Ten hours of “firewood” means a replenishable queue of useful, verifiable slices. It does not mean busywork, duplicated dashboards, or an unlimited wall-clock extension.
| Stage | Shared contract | Evidence of completion |
|---|---|---|
| Source | Named records with stable identity, provenance, revision, freshness and world; explicit unavailable/stale states | A canvas fact can be traced back to the exact source used |
| Canvas | Domain view of selected sources and current decisions; preserves context and selection | Selection and state survive reload; switching domains does not leak state |
| Chat | Conversation bound to the selected source/canvas context; claims cite source records; proposals remain inspectable | A contextual question produces an attributable answer or explicit unknown; stale context is detected |
| Agent | Bounded executable work arising from chat/canvas intent, with scope, preconditions, progress, result and receipt | One authorized action runs, persists its outcome, and updates the canvas; retry does not duplicate the action |
The feedback loop is agent result → new evidence/state → refreshed canvas → next question. A generated suggestion is not proof that an action happened. Cross-domain consistency belongs in the shell/interface contract; domain rules belong in adapters. Reuse existing backend and action machinery where sound, rather than inventing one universal engine before delivering a working slice.
